# 又是怎样设计实验代码的？

程序能够回答问题之后，很自然会想知道：这条寻找材料的路线，到底帮了什么忙？也许答对了一题，但向量检索也能答对；也许这次运行很快，但它用了上次留下的缓存；也许移除了一个步骤，结果变差了，可是回答模型本身也会波动。

实验代码需要让这些疑问有一个可以观察的落点。它安排谁使用什么输入、哪些条件保持一致、哪个步骤发生变化，并留下足够的结果，让后来的人能够回头解释这次比较。

这一章先沿着 Q1 的流程走一遍，再看其他实验为什么需要不同的安排。这里的文件入口对应当前代码；历史运行究竟用了什么输入和协议，要读对应记录。尤其是早期小语料补充实验，不能直接当成当前各入口的默认输入方式。

## 1. 程序跑通以后，还需要弄清什么？

接着上一章的 Alice 例子，如果系统回答 Bristol，会产生几种不同的好奇。

它是不是比直接向量检索更容易答对？它有没有把创办句子和所在地句子一起找回来？Northbridge Institute 的传播是否帮了忙？如果省去 PPR，P1 还会进入上下文吗？语料增加后，要多等多久？

这些好奇观察的对象不同。最终答案、取回的文本、中间计算、耗时和输入规模，不能只用一个总分全部解释。Q1–Q8 就是把它们拆成可以分别处理的问题。

| 想弄清的疑问 | 对应实验 | 主要观察什么 |
|---|---|---|
| 最后回答得怎样？ | Q1 | 预测答案与标准答案的比较 |
| 索引和检索的工作量在哪里？ | Q2 | 分阶段时间、调用与 token 使用 |
| 实体传播和 PPR 起了什么作用？ | Q3 | 移除模块后的检索与回答变化 |
| 找回的材料够不够用、是否相关？ | Q4 | 上下文相关性与参考证据覆盖 |
| 阈值、段落相似度权重改变了什么？ | Q5 | 单个参数变化后的行为与指标 |
| 换嵌入模型会发生什么？ | Q6 | 相同输入下不同嵌入的检索与回答 |
| 材料变多后还能怎样运行？ | Q7 | 不同 token 规模的冷索引表现 |
| 一道题实际经历了什么？ | Q8 | 种子、传播句子、实体与支持段落 |

这里先记住各实验为什么存在。已经取得的分数与结论，集中放在第一部分的[复现报告](../report/scope.md)；具体协议见[实验设计](../../foundation/EXPERIMENT_DESIGN.md)。

## 2. 怎样让两种方法的比较有意义？

想判断检索方法的区别，首先要让它们面对同一件事。两种方法应回答相同的问题，从同一批候选段落中检索，并受到共同的上下文数量约束。否则，一方在更多材料里寻找，另一方的问题更容易，总分差距就很难归因。

项目中常用 Top-5，让每种方法交出五段材料。这给了共同的段落预算，但五段文本的长度仍可能不同，所以它没有同时固定上下文 token 数。理解一个控制条件时，需要同时知道它具体控制了什么。

还要区分问题集合和可搜索语料。比如从问题中抽 100 题，可以只减少回答与评价次数，而让检索继续搜索完整的本地段落集合。若同时把语料也缩成与这 100 题有关的少量材料，检索难度就变了。当前多个实验采用前一种安排，输入清单中用 `corpus_scope="full_source_chunks"` 记录它。

“完整本地段落集合”也有来源边界，它指本地登记的 `chunks.json`，不自动等于公开数据集的全部原文。把问题数和段落数分别记下来，能避免这两种规模在阅读结果时混在一起。

这些安排落实在 [sampling.py](../../../src/datasets/sampling.py) 和 [input_package.py](../../../src/datasets/input_package.py)。前者用固定种子抽取问题，并保留问题的原始顺序；后者把问题、段落、编号与来源描述保存成输入包。文件哈希让之后的读取和恢复能够确认：眼前这份输入还是当时那份。

输入包中的标准答案和参考证据，主要用于评价与回查。当前 Q1 的 `load_inputs()` 只向运行侧交出 ID、问题和答案字段；方法可以把答案转存到 `gold_answer`，但上一章看到的生成提示只拼接检索段落与问题。参考证据和来源映射没有拼入提示。判断是否把答案提供给模型，需要检查实际提示，不能仅凭某个字典里存在 `answer` 字段。

答案生成与评价也需要共同条件。比较中的嵌入模型、回答模型、提示和评价口径都会影响分数。这里登记的本地结果需要生成或 LLM 评价时使用 `qwen3.8-flash`；某些代码入口的默认模型名却仍是 `gpt-4o-mini`。接手者应查看那次运行的 manifest 和记录，明确实际模型，不能用默认值代替已发生的配置。

## 3. 一个实验问题怎样变成可执行的流程？

打开 [Q1 的 generation_accuracy.py](../../../src/experiments/q1_generation_accuracy/generation_accuracy.py)，先找 `main()`。它大致沿下面这条路运行：

```mermaid
flowchart LR
  I[固定输入包] --> M[记录运行条件]
  M --> R[各方法索引与问答]
  R --> V[核对逐题结果]
  V --> E[评价预测]
  E --> C[汇总方法比较]
```

`load_inputs()` 为每个数据集取得问题、段落和缓存位置，同时留下样本 ID、输入哈希、段落数与 LinearRAG 参数。这一步让后面的比较有了共同输入，也让“当时到底用了什么”有处可查。

`main()` 接着构造运行 manifest，记录方法名单、模型、Top-5、默认 BFS 路径和各数据集条件。之后逐数据集、逐方法执行。

`run_vanilla_rag()` 与 `run_linearrag()` 都接收这批问题和段落，各自建立索引，再调用 `qa()`。`run_linearrag()` 通过 `LinearRAGConfig` 显式传入该数据集参数，并设置 `use_vectorized_retrieval=False`。这使实验方法有具体身份：是在比较所引入官方默认 BFS，与本地 Top-5 向量基线。

HippoRAG 则经由 [adapter.py](../../../src/methods/hippo/adapter.py) 调用原始 2024 版实现。适配器把共同输入送到外部实现，并把结果整理回来。接手时需要同时辨认两层：实验调用了哪个接口，接口背后运行了哪个版本。方法名字相近，执行对象也可能不同。

方法返回后，`validate_predictions()` 检查问题与结果是否一一对应、标准答案字段是否一致、是否有预测答案、五段上下文是否来自共同语料。它解决的是结果配错位置或来自错误输入这类具体问题。如果配对已经错了，后面精确到小数点的汇总也没有意义。

把 LinearRAG 这一支单独摘出来，可以看清实验代码如何包住方法调用。下面是调用关系的摘写，省略了其他方法、日志和恢复分支：

```python
questions, passages, working_dir = samples[dataset_name]

predictions = run_linearrag(
    dataset_name, questions, passages,
    embedding_model, llm_model, args.max_workers, working_dir
)
validate_predictions(predictions, questions, passages)

metrics = evaluate_predictions(
    predictions, method_dir, llm_model, args.max_workers
)
```

第一段取得共同输入，中间真正运行方法，后两步核对与评价结果。需要改检索算法时会去方法文件；需要改比较的样本或评价安排时，则在实验与输入代码中寻找对应位置。

随后 `evaluate_predictions()` 保存 `predictions.json`，调用共同的 `Evaluator`，得到两类指标：LLM 判断预测与标准答案是否语义一致；包含匹配检查标准化后的预测文本中有没有标准答案。Medical 在方法比较中报告 LLM 指标，其他数据集会分别报告这两项。

两种指标会有不同的盲点。例如项目中的国籍案例回答 `German`，标准答案为 `Germany`。语义上能对应，字符串包含检查却可能不通过。知道评价器实际执行了什么，才能理解分数为什么与阅读答案的直觉不完全一致。

最后 `compare_methods()` 计算同一数据集中的差值，保存 `comparison.json`，再将数据集汇总到 `summary.json`。实验代码在这里组织和记录比较，核心检索计算仍在各方法实现中。

恢复运行时，Q1 先比较 manifest，再判断预测与评价文件是否已经存在。条件相同时，可以接着使用已完成的阶段。换了问题、模型或配置，应当形成新的运行身份，否则读者难以知道一个目录中不同文件是否属于同一件事。

## 4. 为什么不同问题需要不同的实验安排？

### 回答与材料：Q1 和 Q4 为什么分别观察？

假如模型答对 Bristol，却没有取回 P1，可能是它利用了已有知识，也可能是上下文中其他材料提供了信息。答案正确本身还没有展示检索取回了哪些证据。反过来，两段支持材料已经在上下文里，模型也可能读错。

[Q4 的 retrieval_quality.py](../../../src/experiments/q4_retrieval_quality/retrieval_quality.py) 因而直接检查检索上下文。它先检索，再把问题、上下文和参考证据交给评价器，分别问：这份材料与问题有多相关？参考证据能否从材料中得到支持？这两项允许出现不同方向的变化：取回更多支持事实时，也可能带入更多无关材料。

当前 Q4 对 Medical 问题按类型抽样。这样的安排让不同题型都进入观察范围，而不是让题量更多的类型覆盖其他类型。汇总时再区分各类型表现和整体统计，读者才能知道平均值的构成。

评价本身也有执行边界：当前代码将拼接的上下文截到 20,000 个字符，相关性请求两次评分，参考证据逐条核对支持判断。没有被完整分类的证据还需要补评，不能拿部分分类得到的比例直接代表完整证据集合的召回。评价器也是实验的一部分，它处理了多少材料、是否完成，都影响结果的含义。

### 拆开机制：Q3 究竟移除了什么？

想知道实体桥接是否有用，可以让系统从 Alice 出发，却停止经由句子发现 Northbridge Institute，再观察材料和答案的变化。想知道图排序是否有用，可以保留传播与段落初始评分，直接按初始分数选段落。

[formal_ablation.py](../../../src/experiments/q3_ablation_study/formal_ablation.py) 用 `AblationLinearRAG` 实现这两种安排。`without_entity_activation` 保留问题种子，跳过语义传播；`without_global_importance` 保留实体传播和段落评分，跳过 PPR。这是对论文模块描述的本地操作化定义，作者没有发布可直接核对的消融实现。

这里不能把“去掉实体激活”理解成“系统完全没有实体”，也不能把“去掉 PPR”理解成“变回 Vanilla RAG”。每个变体仍保留了其他环节。明确剩下什么，才知道结果对应哪种改变。

在代码里，跳过 PPR 的决定就落在这段分支上，下面保留了实际调用：

```python
if self.variant == "without_global_importance":
    passage_ids, passage_scores = self._rank_initial_passage_weights(
        passage_weights
    )
    used_ppr = False
else:
    passage_ids, passage_scores = self.run_ppr(
        entity_weights + passage_weights
    )
    used_ppr = True
```

两条分支前面已经算出了同样职责的实体与段落权重。分岔处决定如何把它们变成排名，随后把 `used_ppr` 记入观察信息。这个位置把“想移除哪个作用”和“实际跳过哪段计算”对应起来。

实验还记录传播实体数、PPR 是否执行和 Top-5 变化。它们帮助回答更近的一层问题：代码是否按安排改变了行为？确认这一层之后，再解释最终答案的变化更可靠。

### 调整旋钮：Q5 与 Q6 为什么控制其他条件？

在 Alice 的例子里，提高传播阈值可能使机构线索停止扩展；提高直接段落相似度的权重，可能改变实体线索与文本相似度之间的平衡。若两项同时改变，就很难知道结果是谁造成的。

[Q5](../../../src/experiments/q5_hyperparameter_sensitivity/hyperparameter_sensitivity.py) 采用单因素扫描：改变 `iteration_threshold` 时保持 `passage_ratio` 的基准值，改变后者时保持前者的基准值。代码用 `experiment_points()` 组织这些点，并记录激活实体、检索变化与回答结果。它让一个参数的影响更容易观察，但没有回答两个参数怎样相互作用。

还要留意相同检索结果下的生成与评价波动。Top-5 没变、答案分数变了，就不能直接说检索参数改善了材料。检索变化与回答变化需要同时查看。

[Q6](../../../src/experiments/q6_embedding_model_robustness/embedding_model_robustness.py) 改变的是嵌入模型。它既影响种子匹配，也影响句子与段落相似度，因此改变可能在多个位置出现。各模型需要自己的向量缓存；NER 在语料与抽取身份一致时可以共用。`prepare_model_cache()` 正是在落实这个区别：重复使用没有改变的抽取产物，重新准备已经改变的向量。

### 看工作量：Q2 与 Q7 为什么关心缓存和边界？

用已经整理好的笔记找答案，通常比从头阅读整箱材料快。计算程序也有类似区别：已有 NER 和向量时的运行，不能回答从零准备它们需要多久。

[Q2](../../../src/experiments/q2_efficiency_analysis/efficiency_analysis.py) 为冷索引使用独立、空的缓存。发现中断留下的缓存时，当前入口要求更换实验编号，因为残留产物已经改变了工作量。`isolated_cache` 和 `resumed_cache` 记录的是测量条件，不只是运行状态的装饰。

它分别测初始化、`index()`、第一次 `retrieve()` 与预热后的重复检索。模型加载被放进 setup，冷索引单独计时；热检索前还有一次不计时的预热。GPU 在计时边界同步，让墙钟时间包含实际完成的 GPU 工作。

`timed_call()` 的计时主体很短：

```python
synchronize_cuda()
started = time.perf_counter()
result = function(*args)
synchronize_cuda()
return result, time.perf_counter() - started
```

当 `function` 是 `model.index`，这段时间对应索引调用；当它是 `model.retrieve`，对应检索调用。计时器本身不会替人决定研究范围，传入哪个动作、调用前准备了什么、有没有已有缓存，才决定测出的数字能够回答什么。

Q2 使用 `retrieve()`，省去答案生成；`NoLLM` 对象会在索引或检索意外调用生成模型时失败。这使“此处没有生成式 LLM 调用”成为执行上可核对的边界。HippoRAG 的索引抽取本身会调用 LLM，则要从外部驱动的实际 token 与阶段记录中查看成本。

[Q7](../../../src/experiments/q7_large_scale_efficiency/large_scale_efficiency.py) 进一步改变输入规模。它要求专用输入包中 `prepared_for="q7"`，并检查目标 token 数与实际测得 token 数一致。段落数相同，文本长度也可能不同，所以按 token 约定规模更贴近被处理的文本量；这个 token 口径仍要按构造记录理解。

如果较大的输入在 NER 阶段中断，可以知道这次运行没有完成，以及限制出现在哪里；不能据此填写一个完整索引耗时，也不能将较小输入的成功当作较大规模的验证。工作量记录需要与完成阶段一起读。

### 看一次真实过程：Q8 能带来什么认识？

平均分告诉人结果怎样，轨迹让人看见它怎样发生。[Q8](../../../src/experiments/q8_case_study/case_study.py) 的 `CaseStudyLinearRAG` 在默认 BFS 计算中增加记录，保留起点、选中句子和激活实体。支持段落位置作为观察信息保存，用于检查结果，没有参与排名或生成。

这里可以看到预想路线在哪一步出现、在哪一步被剪掉，支持段落是否仍进入 Top-5。最终正确与中间正确要分别观察：某个实体链接偏了，系统也可能通过其他信号取回材料。

案例的价值在于让机制具体可见。它没有随机抽取大量问题，补充语料还刻意保留了支持段落，所以不能据此估计一般问题的成功率。真实案例的完整解释见[消融与案例分析](../report/mechanisms.md)。

## 5. 一次运行怎样留下可以解释的结果？

当看到某个平均分时，最好能够沿着文件回到组成它的那些题。

以 Q1 为例，`manifest.json` 说明运行条件，`predictions.json` 保存问题、取回段落与预测答案，评价器又把逐题评价写回预测，并保存 `evaluation_results.json`。`comparison.json` 和 `summary.json` 提供汇总。

假设五道教学样题中三道通过某项判定，平均值就是 3/5。这一小段算术没有难度，难的是确认每个 0 或 1 为什么成立：答案表达有没有差别，支持材料是否齐全，判定是否完成，题目与结果是否配对。逐题输出保留这些解释所需的材料。

其他实验还需要不同产物。效率实验要有计时边界和环境；消融需要记录实际路径；参数实验需要保存每个参数点；案例需要保留中间轨迹。因此，不能要求所有实验只留下同一种摘要，也不能只保存终端最后打印的数字。

缓存与结果也各有职责。缓存帮助少做重复计算，结果帮助解释已经发生的运行。恢复一份缓存以后测出的加载或补做时间，有它自己的用途，但不能改称第一次冷索引时间。本项目曾出现这一问题，已有边界说明放在[效率与规模](../report/cost.md)。

目录安排让这些东西有稳定位置：`data/input/` 放输入与模型，`data/cache/` 放可复用中间产物，`data/output/` 放运行结果，`docs/records/` 放解释性记录。具体路径由 [src.paths](../../../src/paths.py) 解析；完整约定见[数据目录说明](../../../data/README.md)。

接手后要找一次运行，先从[实验状态索引](../../EXPERIMENT_STATE.md)进入对应记录，再沿记录回到输出目录。这样可以先知道这次运行想回答什么，再决定需要看哪些原始文件。

## 6. 接手后，怎样完成一次有依据的调整？

假设接手者想弄清：把传播阈值从 0.4 提高到 0.5，是否会使检索少带入无关材料？这个问题可以把前面三章连起来。

在算法层面，阈值影响线索能否继续传播。先形成一个可观察的预期：有些分数处在两者之间的实体会被剪掉，取回材料可能变化。预期还不能保证相关性提高，因为被剪掉的也可能是有用线索。

在代码层面，找到 `calculate_entity_scores()` 中两处阈值判断：当前实体是否扩展，新得到的实体是否接受。再查看实际实验入口传入的 `iteration_threshold`，确认修改的位置会影响本次运行。传播阈值通常属于查询条件，改变它并不等于改变 NER 或嵌入模型。

在实验层面，可以借用 Q5 的单因素安排，固定输入、模型与其他参数，为两个条件分别保留结果。先选一题查看传播实体和 Top-5 是否符合预期，再决定是否需要在固定样本上继续观察。如果疑问是“无关材料是否减少”，还要检查材料相关性；仅有答案准确率不足以回答这句话。

读结果时，再顺着过程回看：实体是否减少，哪些段落发生变化，支持材料是否保留，相关性评价是否完整，答案又怎样变化。几个层次可以有不同方向，不需要硬拼成一个“改善”结论。

这只是说明怎样思考和组织一次调整，本次文档写作没有执行这项实验。实际需要运行时，环境与命令查[运行说明](../../RUNNING.md)，具体实验条件查[实验设计](../../foundation/EXPERIMENT_DESIGN.md)。

到这里，论文中的设计理由、官方实现中的动作和本地实验中的观察就接起来了。以后遇到新的问题，可以从现象找到对应步骤，再让一次范围明确的比较帮助判断它。
