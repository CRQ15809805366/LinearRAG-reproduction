# 索引与检索效率及规模

LinearRAG 的本地索引与检索未调用生成式 LLM，仍占用本地计算资源。共享 HotpotQA 实验中，LinearRAG 首次查询耗时更低，HippoRAG 在缓存问题实体后的热检索耗时更低。完整 HippoRAG 冷索引耗时缺失。

## 计时阶段

Q2 分别登记程序启动与模型加载、索引准备、首次查询和热检索。索引准备区分冷构建与缓存恢复；热检索另区分问题实体抽取的复用状态。

```mermaid
flowchart LR
  A[程序启动与模型加载] --> B{是否已有索引产物}
  B -->|没有| C[冷索引：从输入重新计算]
  B -->|有| D[恢复缓存或检查点]
  C --> E[首次查询批次]
  D --> E
  E --> F[一次不计时预热]
  F --> G[五次热检索批次]
  G --> H[分别记录检索耗时]
```

Q2 把模型加载和启动开销单独记录，表里的索引时间不包含模型加载；查询计时也不包含答案生成与评价。它测量的是检索准备和检索，不能直接解释成用户拿到最终答案所需的时间。

“热检索”仍然执行排序。HippoRAG 在这里复用的是问题 NER，即问题里的实体抽取，不是直接读取上次的段落排名。但它测的是已经出现过的同一批问题，该结果不代表任意新问题的延迟。

## LinearRAG 的 2Wiki 测量

2026-09-20 的实验使用完整本地 658 段 2Wiki 语料、100 道问题、本地 GPU 嵌入和 `en_core_web_trf` NER。它给出两个分开的观察。

| 操作 | 实际结果 | 测量范围 |
|---|---:|---|
| 三次独立空缓存冷索引 | 612.697、637.975、603.330 秒 | 中位数 612.697 秒，约 10.21 分钟 |
| 恢复已有产物与图重建 | 2.417 秒 | 不包含重新获取嵌入和 NER 的全部成本 |
| 五次热检索的每题耗时中位数 | 0.154178 秒/题 | 同一批 100 题；不含答案生成和评价 |

冷索引时仍要做段落、实体、句子嵌入，完成 NER，建立图并写入缓存。这些本地计算仍占用时间与硬件资源。缓存恢复不重复全部中间计算，其耗时不代表冷索引成本。

五次检索均为每题返回五段，计时中位数来自各批次总耗时除以题数后的五个值。它没有描述逐题延迟的长尾。实验用 `NoLLM` 拒绝生成模型调用，索引和检索记录的 LLM 输入、输出 tokens 均为零。这是该阶段零调用的实际验证。

这组实验只有 LinearRAG，因此它建立了本地参照时间，没有建立方法间效率排名。

## 同一 HotpotQA 输入：首次与热检索的排名不同

补充效率实验让两种方法处理相同的 20 题、250 段输入，使用相同的 `all-mpnet-base-v2` 与 Top-5。

| 测量阶段 | LinearRAG | HippoRAG 2024 |
|---|---:|---:|
| 完整冷索引 | 41.7331 秒 | 未获得有效完整观测 |
| 首次查询批次平均每题 | 0.0992 秒/题 | 1.4023 秒/题 |
| 五次热检索批次平均每题耗时的中位数 | 0.0999 秒/题 | 0.0179 秒/题 |

表中小数保留四位，原始精度见证据。

HippoRAG 首次查询包含未缓存的问题实体抽取和排序；热检索复用已抽取的问题实体，重新执行 `rank_docs`。这些条件能够解释为什么两行速度差异很大。首次查询与缓存问题 NER 后的热检索具有不同测量条件，结果不支持跨阶段的统一速度排名。

实际应用的平均延迟还受问题重复比例、服务商响应、模型驻留状态及答案生成时间影响。本次未测量这些条件的组合效果。

## HippoRAG 冷索引观测缺失

HippoRAG 抽取过程中出现缺少 `triples`、输出达到上限等问题，运行通过保留已完成抽取检查点继续完成。后续对 JSON 模式、输出预算和个别段落传输方式作了兼容处理；保留的抽取因此不是统一条件下的一次完整成功冷构建。

最后一次调用记录了 7.7465 秒索引阶段耗时，但它恢复了全部 250 段的抽取检查点，再完成图和运行时准备。该值衡量已有抽取检查点后的索引准备，不包含历史抽取成本，与 LinearRAG 的 41.7331 秒冷索引时间不具备相同计时边界。

实验最终完成了首次和热检索测量，说明这两个结果可用；完整冷索引问题仍然缺一项观测。原始摘要的 `status=passed` 描述最终调用通过，结果记录使用 `passed_with_recovery` 描述整段运行过程。通过状态与成本测量完整性应分别理解。

## 索引规模测量

Q7 没有测回答，也没有测 HippoRAG。它从本地 HotpotQA 来源段落构造确定性的嵌套前缀，使用 `all-mpnet-base-v2` 分词器达到精确的 250K 和 500K tokens，各自执行一次独立空缓存冷索引。索引包含嵌入、NER、图构建和缓存写入，不含模型初始化、检索和答案生成。

两次运行使用 RTX 4050 Laptop GPU；详细 Python、Torch 和 CUDA 版本见原记录。

| 输入 tokens | 段落数 | 索引秒数 | 每百万 tokens 的秒数 | 缓存字节数 | 图顶点数 / 边数 |
|---:|---:|---:|---:|---:|---:|
| 250,000 | 250 | 243.5780 | 974.3121 | 80,757,157 | 15,085 / 22,239 |
| 500,000 | 499 | 462.9087 | 925.8174 | 151,654,004 | 27,861 / 43,493 |

tokens 翻倍，索引时间约变成 1.9005 倍。图规模和缓存体积也随之增大。这两个点的增幅接近按输入规模增长，但每个规模只有一次观测，两个点不足以证明稳定的线性扩展规律。表里的 tokens 来自固定分词器，不能与其他实验的字符数或空白分词词数混用。

1M-token 尝试在 NER 阶段未完成，没有可用完整测量。该尝试未建立 1M 成功结果，也不足以确定算法的规模上限。这里没有论文使用的 ATLAS-Wiki 5M/10M 实验，没有更大规模的基线比较。

## 结果解释与边界

本地证据确认 LinearRAG 索引与检索的零生成式 LLM 调用，并提供特定输入下的时间和规模观测。完整冷索引的方法间比较未完成。查询速度排名随问题 NER 的缓存状态变化，因此结论限定于各自的测量阶段。
